Déployer Nextcloud relié à l'Active Directory

Debian, Apache, MariaDB : comptes AD par LDAP, dossiers d'équipe, HTTPS, client déployé par GPO, édition en ligne avec Collabora.

Auteur
Constant Segrétain
Contexte

Date
septembre 2026
Objectif
Offrir aux utilisateurs du domaine un cloud privé : fichiers synchronisés, partages, agenda, édition de documents, avec leur compte Windows habituel.
Épreuve E6
« Un environnement de travail collaboratif ».
Prérequis
Un domaine AD avec DNS et autorité de certification, un pfSense, un poste client Windows dans le domaine.

1. Nextcloud et architecture

Nextcloud est une solution de cloud privé open source : stockage et partage de fichiers (web, client de bureau, mobile), calendriers, contacts, Talk (chat et visio), édition en ligne. C'est une alternative à OneDrive / Google Drive, et en partie à Microsoft 365, avec des données qui restent sur nos serveurs.

3. Relier Nextcloud à l'Active Directory

Préparer dans l'AD un compte de service sans privilège, par exemple SVC_Nextcloud dans OU=Services, qui sert uniquement à lire l'annuaire. Sur le serveur :

sudo apt install -y php-ldap
sudo systemctl restart apache2

Dans Nextcloud : Applications → activer LDAP user and group backend, puis Paramètres d'administration → Intégration LDAP/AD.

Onglets Utilisateurs, Attributs de connexion, Groupes

  • Utilisateurs : classe d'objet person → Vérifier les paramètres et compter les utilisateurs.
  • Attributs de connexion : cocher le nom d'utilisateur LDAP (sAMAccountName) pour se connecter avec le login Windows.
  • Groupes : classe d'objet group → Vérifier les paramètres et compter les groupes.

4. Groupes et dossiers d'équipe

  1. Dans l'AD, créer des groupes de service (ex. GG_Compta, GG_Direction) et y placer des utilisateurs.
  2. Dans Nextcloud : Applications → activer Team folders (anciennement Group folders).
  3. Paramètres d'administration → Dossiers d'équipe : créer un dossier par service, lui affecter le groupe AD, régler les droits (lecture, écriture, partage, suppression) et un quota.
  4. Se connecter avec plusieurs comptes AD : chacun ne voit que les dossiers de ses groupes.

5. Passer en HTTPS

Certificat demandé à l'autorité interne, avec le nom DNS du serveur en SAN :

sudo mkdir -p /etc/ssl/certs/nc /etc/ssl/private/nc
cd /etc/ssl/private/nc
sudo openssl req -new -newkey rsa:2048 -nodes -keyout nc.key -out nc.csr \
  -subj "/CN=nextcloud.sio.local" -addext "subjectAltName=DNS:nextcloud.sio.local"

Faire signer nc.csr sur https://srv-ad/certsrv (modèle Serveur Web, encodage Base 64), copier le certificat en /etc/ssl/certs/nc/nc.crt, puis créer /etc/apache2/sites-available/nextcloud.conf :

<VirtualHost *:80>
    ServerName nextcloud.sio.local
    Redirect permanent / https://nextcloud.sio.local/
</VirtualHost>

<VirtualHost *:443>
    ServerName nextcloud.sio.local
    DocumentRoot /var/www/html/nextcloud
    SSLEngine on
    SSLCertificateFile    /etc/ssl/certs/nc/nc.crt
    SSLCertificateKeyFile /etc/ssl/private/nc/nc.key
    <Directory /var/www/html/nextcloud>
        AllowOverride All
        Require all granted
    </Directory>
</VirtualHost>
sudo a2enmod ssl rewrite headers
sudo a2ensite nextcloud.conf
sudo apache2ctl configtest && sudo systemctl restart apache2

Ajouter dans config.php : 'overwrite.cli.url' => 'https://nextcloud.sio.local',

6. Déployer le client Nextcloud par GPO

  1. Télécharger le client Windows au format MSI sur nextcloud.com/fr/install. Le déploiement par GPO n'accepte que des MSI.
  2. Le copier sur un partage lisible par les ordinateurs du domaine (lecture/exécution), ex. \\srv-ad\Deploiement$\Nextcloud.
  3. Créer une GPO liée à l'OU des ordinateurs : Configuration ordinateur → Stratégies → Paramètres du logiciel → Installation de logiciel → Nouveau → Package.
  4. Choisir le MSI par son chemin réseau (UNC), pas par un chemin local, puis le mode Attribué.
  5. Sur le client : gpupdate /force puis redémarrage. L'installation se fait au démarrage, avant l'ouverture de session.
ModePar ordinateurPar utilisateur
Attribuéinstallé au démarrageinstallé à l'ouverture de session
Publiéimpossibleproposé dans Programmes → Obtenir des programmes

Première ouverture du client : adresse https://nextcloud.sio.local, connexion avec le compte AD dans le navigateur, puis choix du dossier local et du mode de synchronisation.

7. Édition en ligne avec Collabora

Pour simplifier, Collabora Online (CODE) est installé sur le serveur Nextcloud lui-même, derrière Apache sur le port 444.

cd /usr/share/keyrings
sudo wget https://collaboraoffice.com/downloads/gpg/collaboraonline-release-keyring.gpg

sudo tee /etc/apt/sources.list.d/collaboraonline.sources <<EOF
Types: deb
URIs: https://www.collaboraoffice.com/repos/CollaboraOnline/CODE-ubuntu2204
Suites: ./
Signed-By: /usr/share/keyrings/collaboraonline-release-keyring.gpg
EOF

sudo apt update && sudo apt install -y coolwsd code-brand
sudo coolconfig set ssl.enable false        # Apache chiffre à sa place
sudo coolconfig set ssl.termination true
sudo systemctl restart coolwsd
sudo a2enmod proxy proxy_connect proxy_http proxy_wstunnel ssl

/etc/apache2/sites-available/collabora.conf : Apache porte le certificat et relaie vers coolwsd (port local 9980).

  1. Sur le pfSense, autoriser TCP 444 du réseau clients vers le serveur Nextcloud.
  2. Dans Nextcloud : installer l'application Nextcloud Office.
  3. Paramètres d'administration → Office → Utiliser votre propre serveur → https://nextcloud.sio.local:444.
  4. Créer un document texte depuis l'interface : il s'ouvre dans le navigateur.

  • Mobile : application Nextcloud (Android / iOS), même adresse et même compte.

9. Évolutions (demande E6)

LDAPS : chiffrer le lien avec l'AD

En LDAP simple (TCP 389), le mot de passe du compte de service et ceux des utilisateurs circulent en clair. LDAPS transporte LDAP dans TLS sur TCP 636. Le contrôleur de domaine présente son certificat ; le serveur Nextcloud doit faire confiance à l'autorité qui l'a signé.

  1. Sur https://srv-ad/certsrv : Télécharger un certificat d'autorité de certification → encodage Base 64.
  2. Le copier sur Nextcloud avec l'extension .crt (obligatoire) :
sudo mkdir -p /usr/local/share/ca-certificates/sio
sudo cp sio-ca.crt /usr/local/share/ca-certificates/sio/
sudo update-ca-certificates
openssl s_client -connect srv-ad.sio.local:636 -brief </dev/null   # doit afficher "Verification: OK"
  1. Dans l'intégration LDAP : hôte ldaps://srv-ad.sio.local, port 636, puis retester la configuration.

Déplacer les données hors de la racine web

cd /var/www/html/nextcloud
sudo -u www-data php occ maintenance:mode --on
sudo mkdir -p /var/nextcloud-data
sudo mv /var/www/html/nextcloud/data/* /var/www/html/nextcloud/data/.ocdata /var/nextcloud-data/
# config.php : 'datadirectory' => '/var/nextcloud-data',
sudo chown -R www-data:www-data /var/nextcloud-data
sudo chmod 750 /var/nextcloud-data
sudo -u www-data php occ maintenance:mode --off

Déplacer la base sur un serveur dédié

  1. Nouveau serveur Debian avec MariaDB, même version que la source ; bind-address = son IP dans /etc/mysql/mariadb.conf.d/50-server.cnf ; vérifier avec ss -lntp | grep 3306.
  2. Y créer dbnextcloud et le compte 'usrnextcloud'@'<IP_nextcloud>' avec le même mot de passe.
  3. Nextcloud en maintenance, puis export et import :
sudo mariadb-dump --single-transaction --default-character-set=utf8mb4 -u root -p dbnextcloud > /tmp/nextcloud-dump.sql
# copie du fichier vers le serveur de BDD, puis sur celui-ci :
sudo mariadb -u root -p dbnextcloud < /tmp/nextcloud-dump.sql
  1. config.php : 'dbhost' => '<IP_serveur_bdd>', sortie de maintenance, puis désinstallation de MariaDB sur le serveur Nextcloud.
  2. Si un pare-feu sépare les deux serveurs : ouvrir TCP 3306 de Nextcloud vers la base, et rien d'autre.
