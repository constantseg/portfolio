Relier deux sites par un VPN IPsec sous pfSense

Tunnel IKEv2 entre deux pare-feux pfSense : clé partagée, phases 1 et 2, règles de pare-feu, tests, cas du NAT et authentification par certificat.

Auteur
Constant Segrétain
Contexte
TP B2.1 · conception d'infrastructure réseau
Date
octobre 2026
Objectif
Interconnecter les réseaux locaux de deux sites à travers Internet, de façon chiffrée et authentifiée, comme s'ils étaient reliés directement.
Bloc
B2.1 — « une solution permettant la connexion sécurisée entre deux sites distants ».
Matériel
Par site : un pfSense (WAN + LAN) et un serveur ou poste sur le LAN.

1. Rappels

IPsec sécurise les échanges au niveau IP (couche 3). Entre deux réseaux, on l'utilise en mode tunnel : le paquet d'origine est entièrement chiffré puis encapsulé dans un nouveau paquet IP entre les deux pfSense.

Mode transportMode tunnel
UsageEntre deux hôtesEntre deux réseaux (VPN site à site)
ChiffréDonnées seulementPaquet IP complet
Nouvel en-tête IPNonOui, adresses internes masquées

La connexion se négocie en deux phases, à paramétrer à l'identique des deux côtés :

  • Phase 1 (IKE SA) : les deux pairs s'authentifient (clé partagée ou certificat) et ouvrent un canal de contrôle chiffré.
  • Phase 2 (Child SA) : ils définissent le trafic concerné (réseau local ↔ réseau distant) et son chiffrement (ESP), puis créent le tunnel.
PortRôle
UDP 500 (ISAKMP)Premiers échanges IKE ; toute la négociation s'il n'y a pas de NAT.
UDP 4500 (NAT-T)Si un NAT est détecté : négociation, keepalives et données ESP encapsulées.

Les deux LAN doivent être différents. S'ils se chevauchent, le routage ne sait pas de quel côté se trouve une adresse : il faut alors un NAT en phase 2 (voir § 8).

3. Préparer le WAN (maquette uniquement)

En TP, les WAN sont souvent dans un réseau privé. pfSense bloque par défaut les adresses privées sur le WAN, ce qui empêche les deux pairs de se joindre. Sur les deux pfSense : Interfaces → WAN → décocher Block private networks and loopback addresses → Save → Apply Changes.

En production, avec des WAN publics, on laisse cette option cochée. pfSense ajoute automatiquement sur le WAN les règles qui autorisent IKE, NAT-T et ESP depuis la passerelle distante.

6. Règles de pare-feu

Une fois IPsec activé, pfSense crée l'onglet Firewall → Rules → IPsec. Le trafic qui sort du tunnel y est filtré ; par défaut tout est bloqué. Sur chaque pfSense, ajouter une règle :

ChamppfSense 1pfSense 2
Action / InterfacePass / IPsecPass / IPsec
ProtocolAny (ou ICMP + ports utiles)idem
SourceNetwork 192.168.20.0/24Network 192.168.10.0/24
DestinationLAN netLAN net

Pour un TP, « Any » suffit. En production, on n'ouvre que les flux nécessaires (par exemple SMB vers le serveur de fichiers, RDP vers un serveur précis).

7. Tester

  1. Status → IPsec → Connect P1 and P2 si le tunnel n'est pas déjà monté. La phase 1 doit être Established et la phase 2 Installed.
  2. Depuis le serveur du site 1, ping 192.168.20.10 ; depuis le site 2, ping 192.168.10.10.
  3. Vérifier que les compteurs d'octets de la phase 2 augmentent.

8. Cas particuliers

pfSense derrière un routeur (box)

Si le WAN du pfSense est derrière un autre routeur, sur chaque routeur amont :

  • rediriger UDP 500 et UDP 4500 vers l'adresse WAN du pfSense ;
  • en phase 1, Remote Gateway = adresse publique du routeur d'en face ;
  • My identifier = IP address → adresse publique de son propre routeur (celle que voit le partenaire), et Peer identifier = adresse publique du routeur d'en face.

Le NAT est détecté pendant la phase 1 : la suite des échanges bascule sur UDP 4500 (NAT-T).

Réseaux qui se chevauchent : BINAT

Si les deux sites utilisent le même réseau (ex. 192.168.1.0/24), chacun se présente à l'autre sous une plage virtuelle de même masque, traduite 1 pour 1 par le pfSense.

Phase 2Site 1 (vu comme 192.168.10.0/24)Site 2 (vu comme 192.168.20.0/24)

Depuis le site 1, l'hôte 192.168.1.50 du site 2 se joint alors à l'adresse 192.168.20.50.

9. Bonus : authentification par certificat

Plus robuste qu'une clé partagée : chaque pfSense prouve son identité avec un certificat signé par une autorité que l'autre reconnaît.

Sur pfSense 1Sur pfSense 2
Autorité (System → Certificates → Authorities)Importer la CA 2 (certificat seul, sans clé)Importer la CA 1
Certificat (System → Certificates → Certificates)Certificat du pfSense 1, signé par la CA 1Certificat du pfSense 2, signé par la CA 2
  • Le certificat doit contenir ce qui sert d'identifiant : l'adresse IP WAN (SAN de type IP) si les pairs se joignent par IP, le nom DNS s'ils se joignent par nom. Avec pfSense, on le saisit à la création du certificat ; avec une CA Windows, dans la demande.
  • Phase 1, des deux côtés : Authentication Method = Mutual Certificate, My Certificate = son certificat, Peer Certificate Authority = la CA du partenaire.
  • Status → IPsec → Disconnect puis Connect, et refaire les pings.
