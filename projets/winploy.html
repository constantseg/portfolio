WinPloy

Installer une application sur un lot de postes Windows, maintenant, depuis un poste d'administration.

Type
Projet personnel
Stack
C# · .NET 8 · WPF
Statut
Version 2.0
Code
GitHub

Le besoin

« Installer cette application sur ces douze postes, maintenant. » Intune, SCCM ou WAPT savent le faire, mais les mobiliser pour ça est disproportionné, quand on les a. Je voulais un outil qu'on décompresse, qu'on lance, et qui fait juste ça.

Ce que fait WinPloy

  • Recherche des postes dans l'Active Directory, sans RSAT.
  • Catalogue partagé entre administrateurs : applications WinGet, ou paquets maison (.msi, .ps1, .bat, .exe) posés sur un partage.
  • Une session WinRM par poste, de 1 à 200 postes en parallèle, sans bloquer l'interface.
  • Suivi poste par poste et paquet par paquet, arrêt en cours, relance des seuls échecs, export CSV.
  • Interface en français et en anglais.

Rien n'est installé sur les postes cibles et aucun serveur n'est nécessaire. Ce n'est pas un outil de gestion de parc : pas d'inventaire, pas de conformité, pas de planification. C'est voulu.

Les problèmes intéressants

Copier un paquet sans que le poste accède au partage. Par défaut, les fichiers passent par la session WinRM elle-même, en blocs compressés, avec un cache par empreinte sur le poste cible : un paquet déjà reçu n'est pas renvoyé.

Ne pas ouvrir une faille en exécutant en SYSTEM. C:\Windows\Temp est accessible en écriture aux utilisateurs standards : un utilisateur du poste pourrait remplacer un script juste avant son exécution. WinPloy reconstitue le paquet dans un dossier dont l'héritage des droits est coupé, accessible seulement à SYSTEM et aux administrateurs.

Ne pas faire confiance au dépôt. Qui peut écrire dans le partage peut faire exécuter du code sur tout le parc. Le contenu attendu de chaque paquet peut être figé dans le catalogue, fichier par fichier, en SHA-256. Avant chaque déploiement, WinPloy recalcule et refuse le paquet si un fichier a changé. 

"Files": {
  "setup.msi":   "9f86d081884c7d65…",
  "install.ps1": "60303ae22b998861…"
}

Ce que j'en retiens

J'ai passé plus de temps sur la sécurité que sur la fonction elle-même : le dossier d'exécution aux droits coupés, et les empreintes SHA-256 vérifiées avant chaque déploiement.

La première version était un script PowerShell avec une fenêtre, un poste à la fois. Je suis passé en C# quand il a fallu traiter un lot en parallèle et suivre l'état de chaque poste.
